# PLAN.md — VLESS/VPN клиент (Flutter)

## Статус

Черновик, стадия проектирования. Актуализируется по ходу разработки.

## Цели проекта

- Кроссплатформенный VPN-клиент (Windows, macOS, Linux, Android, iOS) с единой кодовой базой на Flutter.
- Поддержка VLESS через xray-core как первого протокола/ядра.
- Архитектура ядра должна быть **сменной**: возможность заменить xray-core на другое ядро (sing-box, hysteria и т.д.) или запускать **несколько ядер одновременно**, не переписывая UI и остальной клиент.
- Разработка ведётся итеративно: **первая цель — Windows**. Там, где логика неизбежно platform-specific, остальные платформы на первом этапе не реализуются, а фиксируются как задачи на будущее (см. раздел "Бэклог по платформам").

## Нецели (пока)

- Не строим свою реализацию VPN-протоколов — используем существующие ядра (xray-core и т.д.) как чёрный ящик.
- Не делаем поддержку iOS/Android/macOS/Linux в первой итерации — только проектируем так, чтобы их можно было добавить без переписывания ядра абстракции.

## Ключевые продуктовые отличия

Это не "ещё один клиент с другим дизайном" — ниже зафиксированы конкретные проблемы существующих клиентов (v2rayN/v2rayNG, Clash/Mihomo, sing-box клиенты), которые решаем осознанно.

### 1. Единый формат конфига (Magic JSON — MJ)

Проблема: разные клиенты используют разные форматы (xray JSON, sing-box JSON, Clash YAML, голый base64) — конфиги не переносятся между клиентами, каждое ядро поддерживает свой набор протоколов.

Решение — **не форкать xray-core JSON** (это внутренний wiring-формат конкретного движка, вечно догонять апстрим больно), а расширить уже заложенный в плане `CoreConfig` до полноценного **собственного канонического формата профиля**, который:

- описывает серверы, группы (см. п.2) и правила роутинга целиком, а не один outbound;
- **экспортируется** в конфиг конкретного ядра — xray JSON, sing-box JSON, (в перспективе) Clash YAML — через конвертер конкретного `CoreEngine`;
- **импортируется** извне: `vless://`/`ss://`-ссылки, sing-box JSON, Clash YAML, обычные base64-подписки — чтобы пользователь мог принести конфиги из других клиентов;
- расширяется собственными полями ("прикольчиками") без оглядки на апстрим-форматы, т.к. формат наш.

Переключение/комбинирование ядер (xray ↔ sing-box ↔ что угодно) становится просто разными конвертерами из одного Magic JSON-профиля — это напрямую то, ради чего в архитектуре уже был заложен `CoreConfig`.

#### Правило: обратная совместимость Magic JSON — обязательна

Format будет эволюционировать (сейчас уже накопилось: группы, варианты подключения, порядок/скрытие, иконки, подписки — и это не конец списка). Раз формат наш, ломать его нельзя — иначе при каждом обновлении клиента пользователи будут терять профили. Правила:

- У каждого Magic JSON-файла есть поле **`schemaVersion`** (целое число), проставляется при сохранении.
- Новые фичи добавляются **только новыми опциональными полями** со значением по умолчанию — никогда не переиспользуем существующее поле под новый смысл и не меняем тип существующего поля.
- Если поле совсем перестаёт быть нужным — помечаем **deprecated** и перестаём писать, но продолжаем понимать при чтении; физическое удаление поля из парсера — отдельное решение с отдельным поводом, не "заодно с фичей".
- Если всё же нужно структурное изменение (не аддитивное) — пишем **функцию миграции** `migrateVN -> VN+1`, миграции применяются последовательно при загрузке файла со старым `schemaVersion` до текущей версии. Старые миграции не удаляются, пока существуют файлы с той версией "в дикой природе".
- Любой PR, добавляющий поле в Magic JSON, обязан ответить на вопрос: "что произойдёт при чтении файла старой версии этим кодом" и "что произойдёт при чтении файла новой версии старым кодом" (даунгрейд клиента — тоже сценарий, который должен не падать, а по возможности игнорировать незнакомые поля).

### 2. Иерархическая группировка серверов

Проблема: в Clash/Mihomo группировка реализована через "селекторы" — работает, но неудобно и плохо масштабируется на вложенность (группа из групп).

Решение — единый рекурсивный узел `ProxyNode`, где группа и сервер — один и тот же интерфейс:

- **лист** (`ServerLeaf`) — конкретный сервер (один outbound);
- **группа** (`ServerGroup`) — список дочерних `ProxyNode` (серверы и/или другие группы) + стратегия выбора (`select` / `urltest` (автовыбор по задержке) / `fallback` / `load-balance`).

Т.к. группа и сервер имеют общий интерфейс, вложенность не ограничена по глубине без специального кода:

```text
Basic
 - Germany
   - Germany 1
   - Germany 2
 - Poland
```

UI (дерево/аккордеон), роутинг (выбор активного узла) и статистика (агрегация по группе) работают с одной и той же рекурсивной структурой на любом уровне — не нужно отдельно кодировать "группу верхнего уровня" и "вложенную группу". Группы — часть Magic JSON-профиля (п.1), а не отдельная сущность.

### 3. Ручная сортировка и скрытие серверов

Проблема: в большинстве клиентов порядок серверов фиксирован (обычно порядок из подписки/конфига), нет возможности спрятать ненужные без удаления.

Решение — оба свойства живут на уровне `ProxyNode`, а не только `ServerLeaf`, т.к. применимо и к серверу, и к группе целиком:

- **Порядок** — `children` в `ServerGroup` это уже упорядоченный список; drag-and-drop в UI просто переставляет элементы внутри него (и между разными группами, если перетащить в другую). Порядок — часть Magic JSON-профиля, сохраняется как есть.
- **Скрытие** — флаг `hidden` на узле: скрытый узел не показывается в основном списке подключения, но остаётся в профиле (не удаляется), плюс отдельный переключатель "показать скрытые" в UI.

### 4. Несколько инбаундов на одном сервере (варианты подключения)

Проблема, которую описал автор: у одного физического сервера в связке обычно несколько инбаундов под разные протоколы/транспорты (например `vless-tcp-reality`, `vless-xhttp-reality`, `hysteria2`). Наивный подход — завести 3 отдельных `ServerLeaf` — дублирует сервер в дереве/группах втрое и логически неверно: это один сервер, а не три разных.

Решение — `ServerLeaf` хранит не один `ServerConfig`, а список **вариантов подключения** (`variants`) к одному и тому же физическому серверу:

```dart
class ServerLeaf extends ProxyNode {
  final List<ConnectionVariant> variants; // vless-tcp-reality / vless-xhttp-reality / hysteria2 / ...
  final VariantSelection selection;       // manual(id) | auto (urlTest среди variants)
}

class ConnectionVariant {
  final String id;
  final String label;       // "TCP Reality" / "XHTTP Reality" / "Hysteria2"
  final ServerConfig config; // протокол/транспорт-специфичные параметры
}
```

В дереве и группах сервер отображается **одной строкой** (как раньше), а выбор протокола — это либо ручное переключение варианта внутри карточки сервера, либо авто-выбор лучшего варианта по задержке (переиспользуем ту же `urlTest`-логику, что и для `ServerGroup`, просто область применения — не соседние серверы, а варианты одного сервера). Это отдельная сущность от группы намеренно: группа — это выбор *между разными серверами*, вариант — выбор *протокола до одного и того же сервера*.

### 5. Иконки серверов — полный набор эмодзи

Проблема: существующие клиенты определяют иконку сервера автоматически из названия, но матчат только флаги стран (регэксп на код страны/название).

Решение — `icon`-поле на `ProxyNode` принимает **любой эмодзи**, не только флаги:

- автоопределение по названию можно оставить как удобную подсказку (в т.ч. предлагать флаг, если в имени сервера встретилась страна), но это лишь дефолт;
- пользователь может вручную заменить иконку на любой эмодзи через обычный emoji-picker (🚀, ⭐, 🔒 и т.д.), не ограничиваясь набором флагов.

### 6. Метаданные подписки

Проблема: у клиентов часто куце показана информация о самой подписке (просто список серверов без контекста — сколько трафика осталось, когда истекает, что это вообще за подписка).

Решение — вводим сущность `Subscription` в Magic JSON (родитель дерева групп/серверов, а не просто "источник импорта"):

```dart
class Subscription {
  final String id;
  final String name;          // название подписки
  final String url;           // адрес обновления
  final String? pictureUrl;   // лого подписки (произвольная картинка по URL)
  final String? annotation;   // свободный текст — заметки пользователя (сроки оплаты, логин от панели и т.п.)
  final TrafficInfo? traffic; // used / total, парсится из ответа при рефреше
  final DateTime? expiresAt;  // сколько дней подписки осталось — вычисляется от этого поля
  final DateTime? lastRefreshedAt;
  final ProxyNode root;       // корень дерева групп/серверов этой подписки
}

class TrafficInfo {
  final int usedBytes;
  final int totalBytes;
}
```

`traffic`/`expiresAt` заполняются при рефреше подписки — часть общего flow "Рефреш подписки" (см. "Базовые функции" ниже), парсится из ответа сервера (например заголовок `subscription-userinfo`, как это принято у Clash-совместимых панелей) либо из кастомного API, если панель его отдаёт.

## Базовые функции (обязательный набор для MVP+)

Стандартный набор, без которого клиент неполноценен — не отличительная фича, но обязательная база:

- **Режимы подключения — Proxy и TUN.** На Windows это уже описано как Вариант B (системный прокси) и Вариант A (TUN через `wintun`) в разделе "Ядро №1: xray-core" — на других платформах тот же выбор режима будет реализован через их нативный TUN-механизм (см. "Бэклог по платформам"). Режим — параметр сессии в `EngineManager`, не свойство ядра.
- **Пинг всех серверов** — массовый latency-тест по всем `ProxyNode` (и по всем `ConnectionVariant` внутри `ServerLeaf`), переиспользует ту же `urlTest`-логику, что и авто-выбор в группах/вариантах.
- **Рефреш подписки** — по `Subscription.url` подтягивается свежий список серверов (пересобирает дерево `ProxyNode`, желательно сохраняя `hidden`/порядок/выбранные варианты там, где сервер не изменился) + обновляет `traffic`/`expiresAt`.
- **Показ трафика** — used/total из `TrafficInfo`, обновляется при рефреше.
- **Срок действия подписки** — сколько дней осталось, вычисляется из `expiresAt`.
- **Название и annotation подписки** — `name`/`annotation` из `Subscription`, оба редактируются пользователем локально (annotation в первую очередь — это заметки пользователя, не то что приходит с сервера).

## Core Abstraction Layer (Dart)

### `CoreEngine` — интерфейс ядра

Общий контракт для любого VPN-ядра (xray-core, sing-box, ...):

```dart
abstract class CoreEngine {
  String get id;          // уникальный id инстанса (для мульти-ядра)
  CoreType get type;       // xray | singbox | ...
  Stream<EngineStatus> get statusStream;
  Stream<EngineStats> get statsStream; // трафик, задержка и т.п.

  Future<void> start(CoreConfig config);
  Future<void> stop();
  Future<EngineStats> currentStats();
}
```

### `CoreConfig` — унифицированная модель конфигурации (Magic JSON, MJ)

Это и есть Magic JSON из раздела "Ключевые продуктовые отличия": полный профиль (протокол, адрес, порт, id/uuid, transport, tls-параметры, дерево групп `ProxyNode`, правила роутинга), из которого каждая реализация ядра генерирует свой нативный конфиг (для xray — JSON конфиг xray-core). Импорт (`vless://`, сторонние форматы) и экспорт в формат конкретного ядра происходят на этом уровне, а не внутри конкретного движка.

#### `ProxyNode` — дерево серверов/групп

```dart
sealed class ProxyNode {
  String get id;
  String get name;
  String? get icon;  // любой эмодзи, не только флаги — см. "Иконки серверов"
  bool get hidden;    // скрыт из основного списка, но остаётся в профиле
  // порядок задаётся позицией в List<ProxyNode> родителя (children) — отдельного поля не нужно
}

class ServerLeaf extends ProxyNode {
  final List<ConnectionVariant> variants; // vless-tcp-reality / vless-xhttp-reality / hysteria2 / ...
  final VariantSelection selection;       // manual(id) | auto (urlTest среди variants)
}

class ConnectionVariant {
  final String id;
  final String label;        // "TCP Reality" / "XHTTP Reality" / "Hysteria2"
  final ServerConfig config; // протокол/транспорт-специфичные параметры (адрес, порт, uuid, tls...)
}

class ServerGroup extends ProxyNode {
  final List<ProxyNode> children; // серверы и/или вложенные группы — без ограничения глубины, порядок = порядок списка
  final GroupStrategy strategy;   // select | urlTest | fallback | loadBalance
}
```

### `EngineManager` — реестр и оркестрация

- Хранит активные инстансы `CoreEngine` (поддержка одновременного запуска нескольких ядер/профилей).
- Отвечает за выбор реализации по `CoreType` (фабрика/DI, напр. через `get_it` или Riverpod provider).
- В будущем: маршрутизация трафика между несколькими активными ядрами (мульти-хоп, split-tunneling по профилям) — не проектируем детально сейчас, но интерфейс это не должен блокировать.

## Ядро №1: xray-core

### Стратегия для Windows (первая итерация)

Берём готовый бинарник **`xray.exe`** (или собираем сами из исходников xray-core) и управляем им как **подпроцессом**:

- Генерируем JSON-конфиг xray-core из `CoreConfig`, кладём во временный файл.
- Запускаем `xray.exe run -c config.json` через `Process.start`.
- Управление/статистика — через встроенный **Stats API** xray-core (gRPC или HTTP, `api` секция в конфиге) либо через парсинг логов как fallback.
- Остановка — graceful kill процесса.

Почему subprocess, а не FFI, на первом этапе:

- Быстрее для старта на десктопе, не требует сборки cgo-биндингов.
- На Windows нет ограничений на дочерние процессы (в отличие от iOS, где subprocess из VPN-расширения невозможен).
- Абстракция `CoreEngine` скрывает этот выбор — при переходе на мобильные платформы `XrayEngine` для Android/iOS будет отдельной реализацией через `gomobile bind` (`.aar` / `.xcframework`) и FFI/platform channels, не меняя контракт.

### Системная интеграция VPN на Windows

- Вариант A: xray-core поднимает локальный SOCKS/HTTP прокси, а клиент дополнительно поднимает **TUN-интерфейс** (например через `wintun`) и заворачивает трафик через xray — полноценный VPN-режим "для всей системы".
- Вариант B (проще для MVP): системный прокси (задать прокси в настройках Windows через реестр/`WinINet`) без TUN — работает не для всего трафика, но быстрее в реализации.
- Решение: начать с **варианта B** для самого первого сквозного прототипа (подключился → виден трафик через xray), затем перейти к **варианту A** (TUN, полный VPN) как более приоритетной задаче перед релизом на Windows.

## Бэклог по платформам (после Windows-MVP)

Каждый пункт — будущая задача, не блокирует текущую работу:

- **Android**: `VpnService` (Kotlin) + xray-core через `gomobile bind` (`.aar`), TUN через `VpnService.Builder`.
- **iOS**: `NetworkExtension` / `PacketTunnelProvider` (Swift) + xray-core через `.xcframework`. Subprocess невозможен — ядро работает in-process в расширении.
- **macOS**: похоже на Windows-вариант A, но TUN через `utun`, системная интеграция через `NetworkExtension` (Packet Tunnel) или `System Extension`.
- **Linux**: TUN через `tun/tap`, xray-core как подпроцесс (аналогично Windows).

## UI-стек

- **shadcn_ui** — основной UI-кит для кастомного, современного дизайна (вместо стокового Material/Fluent). Даёт полный контроль над темой (тёмная/светлая, акцентные цвета), не завязан на конкретный платформенный вид.
- Стейт-менеджмент: `riverpod` (связка UI ↔ `CoreEngine`/`EngineManager` из Core Abstraction Layer).
- Системная интеграция под Windows (трей, автозапуск, нативные диалоги) — рассматривать отдельно от UI-кита, т.к. shadcn_ui не покрывает OS-level виджеты (tray icon и т.п.), понадобится отдельный пакет (`tray_manager`, `window_manager`).
- На будущих платформах (Android/iOS) shadcn_ui остаётся тем же — дизайн кастомный и платформо-независимый, поэтому отдельный Material/Cupertino слой не потребуется.
